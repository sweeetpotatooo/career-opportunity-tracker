# 공고별 제출 요건과 경험 연결

## 한국 공고를 읽는 단위

한국 공고의 공채·수시, 체험형·전환형, 공개 채용 플랫폼·회사 지원 폼을 구분하되 이름으로 요건을 추정하지 않는다. 하나의 공채 안에서도 실제 지원 직무·차수·마감·문항이 다를 수 있다. 고용형태와 전환 가능성은 원문 그대로 기록하고 전환을 보장하지 않는다.

지원 안내/공개 지원 폼에서 실제 요구하는 이력서·경력기술서·자기소개 문항·포트폴리오·증빙·양식·파일 형식·용량을 확인한다. 문항마다 질문과 글자/바이트 수, 공백 포함 여부, 언어를 남긴다. 로그인 뒤에만 보이면 `지원 폼 확인 필요`로 남기고 자료를 만들어 추정하지 않는다. 시험·과제·면접 유무와 AI 사용 허용 범위도 명시된 것만 기록한다.

- **공고 필수:** 실제 명시된 제출물·문항·제출 순서·제한·전형과 근거 URL/확인일
- **추가 제안:** 역할에 맞는 선택적 사례·데모·포트폴리오. 회사 필수 제출물과 구분
- **준비 현황:** 사용자 확인 또는 이 작업에서 실제 작성한 범위만 반영. 조사했다고 초안 작성/제출 완료로 바꾸지 않는다.

예: 자유 이력서만 요구하는 공고에 자기소개서 4문항·ATS PDF를 기본으로 만들지 않는다. 고정 문항이 있으면 범용 영문 이력서보다 해당 질문·분량·지원 화면 요건을 우선한다. ATS 최적화는 근거 없는 키워드 반복이나 숨김 텍스트가 아니다.

## 같은 경험을 역할에 맞게 연결

먼저 사용자가 지정한 원본 이력서·증빙·프로젝트 기록에서 **문제 → 본인 판단/기여 → 실행 → 확인된 결과 → 한계**를 뽑는다. 프로젝트 이름이 같아도 강조할 증거는 달라진다.

| 역할 | 증거로 찾을 내용 | 준비할 설명 |
| --- | --- | --- |
| 백엔드·시스템/API | 데이터 모델·권한·인증·외부 연동, 오류 재현·테스트, 배포·운영 | 어떤 제약이 있었고 설계/검증으로 어떻게 해결했는지 |
| AI PO/PM·솔루션·BizOps | 사용자 문제·우선순위·업무 흐름, 가설/MVP, 엔지니어 협업·실제 도입·피드백 | 기능보다 해결하려던 문제와 선택의 이유, 효과를 어떻게 검증했는지 |
| HRD·HR AX | 교육·승인·수료 등 운영 흐름, 현업 요구, 도입·변화관리·학습 데이터 | 교육 운영 문제와 시스템 개선의 연결, 운영자/학습자의 변화 |

직무 설명을 실제 경험과 연결하되 원본 사실을 직무마다 바꾸지 않는다. AI 활용은 도구 선택·검증·실패 대응까지 근거가 있을 때 적는다. 프로젝트의 대상 인원/잠재 사용자를 실제 활성 사용자로, 테스트 결과를 사업 성과로, 팀 전체 성과를 개인 성과로 바꾸지 않는다. 확인된 수치만 사용하고 전후 지표가 없으면 임의 개선율을 만들지 않는다.

공고마다 2~3개 핵심 사례와 부족한 근거·필수 기술·도메인 준비를 제시한다. 동일 경험을 여러 문항에 쓰지 말라는 보편 규칙을 만들지 말고 질문별로 증거가 중복되는지 판단한다. 별도 요청이 없으면 모든 후보의 지원서를 자동 작성하거나 제출하지 않는다.

## 작성 요청을 받은 경우

회사 요구 양식과 질문에 맞춰 초안을 만들고 개인 사실·기여·수치·분량을 확인한다. 글자/바이트 계산은 회사 기준에 맞추며 최종 지원 화면의 계산이 있으면 이를 우선한다. 제출본 확정과 실제 지원 완료는 별개다. PDF 등 최종 파일은 사용자가 요청하거나 실제 제출에 필요할 때 만든다.
